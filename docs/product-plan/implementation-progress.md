# EDITH implementation progress

20 November 2026. Active objective: the complete centralized household speaking assistant, using the existing UI. **The overall goal remains incomplete and active.** This is a backend milestone, not a release claim. The user selected WhatsApp Business API as the first contact channel and reviewed merchant checkout as the first order/payment workflow, using their own Shopify store. Home Assistant setup remains deferred.

## Implemented and verified in this milestone

- A real Rust hub in `hub/`, separate from the unfinished `prototype/`: authenticated paired client roles, SQLite transactions, source ownership, child-approved household visibility, FTS5 chunks, persistent vectors and source-version citations. Schema v7 includes reminders, email/phone contacts, email proposals and separate commerce cart/checkout journals while migrating earlier records.
- Python knowledge tools connected to the existing agent. Private paired conversations use local inference from their first utterance; retrieved text cannot cause cloud fallback or unscoped tool execution. Shared guests/children and adult/elder clients have explicit tool allowlists. Legacy global stores are not silently assigned to a new person.
- Optional installed Ollama runtime reuse, with local-model metadata checks and no implicit download. The old llama-cpp path remains available.
- Hybrid local RAG: Nomic v1.5 vectors bound to the installed model digest, owner-only chunk export, atomic version-bound indexing, cosine/keyword fusion after permission filtering, optimistic source updates and vector invalidation. Keyword fallback is labelled. Retained citations and paired identity are revalidated around model calls and before tools; unverifiable/stale context is discarded.
- Durable `home.power` proposals, exact argument-hash approvals, single execution claims, immutable result evidence and unknown-outcome recovery. A production database ownership lock prevents another process from interrupting a live journal.
- A Home Assistant adapter and trusted coordinator library, tested against local/synthetic services. **Home Assistant setup is deferred at the user's request.** No physical device was operated; the coordinator is not an LLM approval tool.
- Strict affirmative parsing, bounded microphone buffering, capture-side mute discard and stale-transcript invalidation. Foreground verification and bounded/constrained taught-task recipes protect the existing desktop adapters.
- A bounded, worker-owned TTS engine with cancellation, stale-generation admission, safe backend repeat and rate control. Existing mute now cancels future agent/tool work and speech; captured request generations survive queued turns. Voice rate commands are local. This does not abort a blocking provider/native call or undo effects already in flight.
- Durable one-time reminders, with member scope, exact-time confirmation, idempotent creation, leased announcement, tracked TTS outcomes and restart recovery. They announce only while the matching private session is running, unmuted and outside an active conversation. Acknowledgement does not prove task completion. Wake detection excludes EDITH's own speech and retains the accepted audio snapshot across conversation-lock admission.
- Member-owned contacts now support email and/or explicit international phone numbers. Duplicate names return choices. Contact changes advance a revision and invalidate stale email approval; a phone-only record cannot create an email proposal. Contact storage does not imply WhatsApp opt-in or account availability.
- Optional Gmail email journal, one-attempt coordinator and exact review/send commands outside the model. Full verified sender, recipient and content readback must complete before fresh confirmation. Approved provider attempts are claimed once; interrupted or ambiguous outcomes remain unknown. API acceptance is not recipient delivery.
- Explicit per-member Gmail OAuth setup and protected credential refresh, separate from legacy Google stores. No startup browser login; signed identity verification, restricted local files, atomic rotation, refresh locking and cancellation checks before provider submission. This optional implementation is retained while WhatsApp Business takes priority; no Gmail account was connected.
- An own-store Shopify flow through the existing voice UI: exact allowlisted merchant configuration, bounded catalog search, local proposals from recently observed variants/prices, trusted full readback, fresh re-quote before one cart-create attempt, and a separate freshly reviewed checkout-opening claim. Changed prices, store configuration or access block stale actions. Model tools cannot create carts, open checkout or submit payment. Local setup supports tokenless access or a protected public Storefront token; the actual store domain/account is still pending.
- WhatsApp Business foundations pinned to Graph v26.0: protected selected-token reads, explicit WABA/phone verification, exact approved body-template snapshots/rendered parameters and read-only verification CLI. Standalone text/template senders require both trusted approval and recipient policy, make one POST and distinguish acceptance from delivery. Trusted consent/window records, the central business-message journal, voice sending and signed event ingestion remain unfinished; no WhatsApp send tool or real account is connected.
- Scoped project tools read/search and stage reviewable replacement diffs. Canonical paths, source versions and proposal hashes bind the operation; the model has no apply/execute tool. Protected owner project configuration is available for EDITH. The code-worker module reports unavailable until a real sandbox is provisioned and tested.
- Child mode runs finite, fixed word/maths games and fixed fallback responses without model calls. Elder mode uses respectful single-step wording. These are configured client modes, not recognition of who is speaking.
- Telegram accepts the configured sender in a private chat and has public-information tools only. It no longer inherits desktop scripts, private knowledge or taught-task metadata.
- Local setup/import CLI and a launcher that uses the existing interface. Protected current-user/SYSTEM configuration was initialized under `D:\CodexTools\edith-household`; no credentials were printed or stored in Git.

## Requirement-by-requirement remaining work

| Requirement | Current evidence | Still needed |
|---|---|---|
| Advanced speaking assistant | Existing wake/STT; cancellable TTS and turn admission; mute integration; real local model reasoning | Faster responses, acoustic barge-in, genuine microphone/noise/language evaluation, room sessions, blocking-call cancellation |
| Rust central coordination | Authenticated local service, durable journal, single process ownership | Trusted member interaction, pairing/revocation lifecycle, all configured connectors behind common policy and worker credentials |
| RAG | Permission-filtered hybrid retrieval, a grounded local answer, updates and cached-citation revalidation | Broader parsers, memory migration, larger-library quality/performance, total token budgeting |
| Central home | Adapter + journal/coordinator tested with synthetic services | Trusted approval integration; physical device configuration and live acceptance deferred until Home Assistant setup |
| Code development | Scoped read/search/patch proposals; trusted apply API; model cannot execute/apply; worker reports unavailable | Authenticated patch review/application flow, real isolated execution/testing, credential isolation and controlled publishing |
| Child play and learning | Curated offline games, fixed fallback, per-game limits; no open model/tool calls | Parent controls, age bands, wider reviewed learning material, daily/session policy and field evaluation |
| Elder help | Equal authority, single-step wording, rate controls, durable one-time reminders, full email readback | Recurring schedules, broader accessible trusted approvals, voluntary delegation and acoustic acceptance |
| Orders and payments | Own-store catalog/local proposals, central cart/checkout journal, protected configuration, exact voice review and separate opening claim; synthetic full-path acceptance | Actual store/domain connection and live acceptance, order/payment/receipt/refund reconciliation |
| Contact people | Scoped contacts, optional Gmail flow; WhatsApp Business account and approved-template adapters with default-deny policy | Actual WhatsApp account, trusted consent/business-message journal/voice integration, verified service-window policy, signed delivery events and calls |
| Recommendations | Public information helpers and local model answers | Current sources/catalogues, constraints, source dates, comparison quality and sponsorship disclosure |
| Operations | Local setup, configuration, lockfile, tests and restricted data directory | Installer/update/rollback, backups/restore, credential rotation UX, model budgets, support and field evaluation |

Next implementation work should extend these real services without replacing the UI. Backend milestones must not be presented as completion of the still-open requirements above.
