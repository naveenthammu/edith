# EDITH updated source assessment

20 November 2026 · Reviewed upstream commit `a006344`

EDITH is now a substantial single-user Python desktop assistant. It has implemented voice, model routing, tool execution, memory, desktop automation and account integrations. The earlier assessment of a small historical script is no longer the current implementation baseline. This review supports the broader [household blueprint](household-agent-blueprint.md); it does not reduce that vision to desktop automation.

The recommended direction is to reuse the Python voice/model/integration adapters beneath a staged Rust control plane. Preserve reusable code while adding household identity, scoped knowledge, durable actions, cancellation and isolated execution. Rewriting every adapter in Rust would not, by itself, supply those missing product capabilities.

This is a source assessment, not a complete formal security audit. No live application, microphone, screen capture, model inference, provider API, messaging, browser automation or device integration was exercised for this assessment. No dependencies were installed and the repository's pytest suite was not run. A separate standard-library check parsed tracked Python files and exercised two extracted pure functions with synthetic inputs; see [verification evidence](current-review-evidence.json). Source references below use repository-relative `path:line` locations at the reviewed commit, except explicitly identified untracked prototype files. Provider availability, SDK compatibility, model quality and runtime performance remain unverified.

The current inventory contains **57 tracked files, 44 Python files, 62 skill declarations and 149 test function definitions**. Parametrized test cases are not expanded in that count. Thirteen skills opt into the confirmation flag and 49 do not; this describes metadata, not the appropriateness of each action's policy. All 44 Python files parsed successfully, which establishes syntax only.

## Current implementation, local work and target

Three different things must remain separate:

1. **Tracked upstream Python application:** the implementation described below, invoked through `main.py`. Its code is real; presence of a tool is not proof of a successful live integration.
2. **Untracked local Rust/React prototype:** unfinished work under `prototype/`, outside commit `a006344`. `prototype/hub/src/app.rs:12` returns an empty Axum router, its `AppState::new` ignores the supplied paths (`prototype/hub/src/app.rs:7`), and `prototype/hub/src/lib.rs:1` exports only `app`. Additional domain, storage, retrieval, model and voice source files do not establish connected HTTP functionality. Neither the first-prototype contract nor the presence of a UI establishes a working household product.
3. **Full household target:** a centralized, multi-person system for speaking, home control, RAG, software development, child play/learning, elder assistance, shopping/payments, contacts and recommendations. This remains the product scope. Each domain needs implementation and acceptance evidence beyond its closest existing desktop tool.

“Implemented” below means an executable source path exists. “Unit coverage” means fake/synthetic tests are present, not that they were run here. “Missing” means no corresponding product implementation was identified in the reviewed upstream application; it does not deny the existence of related helper code or unfinished local work.

## Priorities before expanding authority

The following priorities concern the intended product, not a claim that each item is an independently validated vulnerability. Preserve useful adapters while enforcing these controls at a common execution boundary.

### Priority 1: identity, exact actions and reliable outcomes

- **Bind permission to a person and an exact action.** Voice confirmation accepts any utterance containing the word “yes” (`main.py:17`), so a sentence such as “I did not say yes” passes. The confirmation listener has no authenticated speaker or action-bound approval object (`main.py:141`). Telegram uses a similar yes-word check (`skills/telegram.py:85`). Replace this with explicit confirmation states, canonical arguments, identity, expiry and invalidation when targets/terms change. Keep the existing confirmation hook as an adapter.
- **Apply policy to indirect desktop effects.** The registry defaults to no confirmation (`skills/__init__.py:36`), and typing/keyboard shortcuts are available without confirmation (`skills/computer.py:169`, `skills/computer.py:188`). An LLM can reach an external effect through low-level UI operations as well as a named send/delete tool. A tool flag and a prompt instruction are not a complete action policy.
- **Journal effects independently of model history.** Tool execution returns strings (`brain/agent.py:139`). If a later model request fails, the whole current turn is removed from history (`brain/agent.py:94`), including prior successful effects. Add durable operation IDs, state transitions, idempotency and reconciliation. Distinguish proposed, approved, submitted, completed, failed and unknown outcomes. Do not retry an uncertain order/payment as a new transaction.
- **Verify focus before entering data.** On Windows, `focus_window` catches activation errors and subsequently returns True (`skills/screen.py:103`, `skills/screen.py:124`). `type_text` trusts that result (`skills/computer.py:177`), as does the WhatsApp send path before pressing Enter (`skills/computer.py:425`). Confirm the actual foreground target and refuse on mismatch. WhatsApp currently reports opening a chat and pressing Enter (`skills/computer.py:429`), not a verified message status.
- **Separate household accounts and remote actors.** Google uses one token path (`skills/google_apps.py:19`) and one authorized account per store (`skills/google_apps.py:38`). Telegram checks chat ID but not sender identity or private-chat type (`skills/telegram.py:49`); configuring a group chat would authorize text from that chat rather than one verified person. Add principal/device pairing, account-scoped credentials and explicit remote command permissions. Voice and Telegram also share the same memory object (`main.py:136`, `main.py:148`).
- **Isolate code execution.** Scripts explicitly run with the desktop user's full permissions (`skills/computer.py:355`); the interpreter wrapper is not a sandbox (`skills/computer.py:335`). Build coding workers with disposable workspaces, resource/network controls, separate secrets and reviewable patches/test evidence. Do not expose unrestricted script execution to child, guest or general remote sessions.

### Priority 1: cancellation, listening and private data

- **Implement interruption across the whole turn.** `converse` synchronously waits for `agent.handle` and then TTS (`main.py:86`). Listener waits for speech to end and drops buffered audio (`voice/stt.py:121`), while Speaker provides a speech queue without a stop operation (`voice/tts.py:19`). “Stop” only exits when it reaches the next ordinary transcription (`main.py:82`); it cannot reliably interrupt speech, inference or an executing tool. Add cancellation tokens, turn IDs, stoppable playback and stale-result suppression. Refusing one tool presently returns a cancellation string while other tool calls can continue (`brain/agent.py:118`, `brain/agent.py:145`); define task-level cancellation too.
- **Make mute and buffering match the privacy promise.** InputStream continually copies raw audio into an unbounded queue (`voice/stt.py:75`). The mute Event substitutes zeros only as chunks are consumed (`voice/stt.py:90`); the overlay does not stop capture (`ui/overlay.py:25`). Bound the buffer, discard at capture while muted, clear on transitions and offer an accurate capture indicator. A slow model/tool should not accumulate arbitrary room audio in memory.
- **Limit retention and cloud disclosure.** Spoken transcripts, replies, tool arguments and learned facts can enter ordinary logs (`main.py:80`, `brain/agent.py:82`, `brain/agent.py:115`, `brain/agent.py:120`, `config.py:42`). All stored facts and taught-task summaries enter model context (`brain/agent.py:153`), which online adapters transmit (`brain/llm.py:157`, `brain/llm.py:211`). Add per-person storage scopes, redacted diagnostics, retention/deletion, data-class cloud permissions and private reply destinations. Existing prompt text that treats external content as untrusted (`brain/agent.py:32`) is useful guidance, but ordinary code must enforce permissions.
- **Constrain teaching capture and replay.** The credential filter only looks for a few words in the active window title (`skills/teach.py:24`, `skills/teach.py:112`, `skills/teach.py:122`). Keystrokes and click crops are recorded outside those titles (`skills/teach.py:163`, `skills/teach.py:175`), then events/crops are sent to the vision model (`skills/teach.py:247`). It is not field-level secret detection, and non-Windows active titles are empty. Add explicit capture scope, visible recording state, review/redaction and consent before upload.
- **Validate recipes and confine assets.** `parse_compiled` checks that a step has one recognized action key, without complete field/type/bounds validation (`skills/teach.py:76`). Replay joins the recipe's crop value to a folder and can read it without confinement (`skills/teach.py:269`, `skills/teach.py:286`); an absolute/traversing recipe path can refer outside its task directory. Validate model-generated and edited recipe files, resolve/check paths, bound coordinates/steps/waits, preview effects and verify postconditions. The existing mouse-corner fail-safe (`skills/teach.py:335`) is useful but does not replace cancellation or authorization.

### Priority 2: knowledge, model context and persistent services

- **Build real RAG alongside editable memory.** Retain lightweight facts/notes, but introduce source ingestion, stable source IDs, permission filters, lexical plus evaluated semantic retrieval, citations, freshness, conflicting-evidence handling and deletion/revocation propagation. `Memory.facts` reads a single plain-text file (`brain/memory.py:12`); loading facts into a prompt is not document retrieval.
- **Budget context and preserve tool semantics.** History is trimmed by ten user turns (`brain/agent.py:163`), while every registry schema and all facts are supplied (`brain/agent.py:109`, `brain/agent.py:156`). Local context is fixed at 8,192 tokens (`brain/llm.py:347`). Only tool result strings get a 500-character cutoff (`brain/llm.py:89`), and local conversion retains only the first tool call from each assistant message (`brain/llm.py:90`). Add token budgeting, summarized history, explicit truncation and complete multi-tool conversion. Test useful work, not only valid JSON.
- **Make reminders and workflows durable.** Timers are daemon threads with no persisted schedule (`skills/productivity.py:19`). Add restart-safe scheduling, cancellation, time-zone semantics, delivery state and missed-event handling. General task coordination belongs in the Rust action service; do not infer it from a daily Naukri loop.
- **Provision and measure fallback.** Startup can download models, start a proxy, begin listening and enable configured bots/scheduled integration activity (`main.py:121`, `main.py:133`, `main.py:139`, `main.py:148`). Whisper/Vosk/local-model download paths are real (`voice/stt.py:112`, `voice/wake.py:19`, `brain/llm.py:406`). Offline operation requires prior provisioning; “first launch without internet works” is not established. Measure latency, memory, startup, cancellation and task success on the actual host.

## Preserve the complete household delivery scope

| Stage | Deliverable built on this baseline | Required acceptance evidence |
|---|---|---|
| Execution foundation | Rust identity/session/policy/action service; typed Python adapter boundary; bounded voice buffers and cancellation; separate credentials; isolated coding worker | Cross-user denial, exact approvals, interrupt/mute tests, restart/unknown-outcome recovery, no implicit access to household secrets from code workers |
| Home and knowledge | Home Assistant adapter, permitted rooms/entities/scenes; scoped source ingestion/RAG and editable memory | Physical device state verification, offline/manual control, retrieval citations, source freshness, permission revocation and deletion tests |
| Coding and family experience | Repository search/explanation, proposed patches/builds/tests/diffs; curated child play and parent controls; accessible elder controls/reminders/delegation | Meaningful coding checks and isolation evidence; age-banded content evaluations; no child commerce; elder usability, repeat/cancel and independently authorized assistance |
| Commerce and communication | Approved merchant/contact connectors, priced carts, action-specific approvals, trusted payment handoff, order/message status and receipts | Sandbox then explicitly authorized live checks; changed price/recipient invalidates approval; duplicate/timeout reconciliation; never label pending/unknown as completed |
| Recommendations and rollout | Current sourced options, preference/constraint explanations, timestamps and uncertainty; operational budgets and deployment support | Research/source quality, live catalogue accuracy, task success/cost measurements, privacy and multilingual/multi-room evaluations, backup/update recovery |

Do not count browser navigation as an order API, a payment page as payment success, a saved phone number as a verified contact service, a timer as a care system, or script execution as an isolated developer agent. Conversely, do not erase the real upstream adapters when describing the work remaining. The integration boundary should let them evolve independently of household authority.

## Test evidence and safe verification boundary

The [verification record](current-review-evidence.json) reports zero syntax errors across 44 tracked Python files, normalized source agreement with the Git index, and isolated pure-function probes without importing EDITH. The probes reproduced `True` from confirmation inputs `do not say yes` and `no, not yes`; plain `no` was rejected. Recipe parsing accepted synthetic traversal and absolute crop-path strings unchanged, while rejecting an unknown action and invalid JSON. No crop file was read or replayed. These checks support the specific findings above; they are not an end-to-end voice or action test.

No pytest pass count is claimed. Existing tests demonstrate the authors' intended behavior and provide a starting regression suite:

- Agent tests use `ScriptedLLM` and synthetic functions (`tests/test_agent.py:20`, `tests/test_agent.py:33`). They cover tool loops, confirmation, history, learning and failure paths, not live model decisions or account effects.
- Voice tests bypass the Whisper constructor and use synthetic audio/fake microphones (`tests/test_stt.py:10`, `tests/test_stt.py:23`, `tests/test_stt.py:130`). Wake tests check string matching (`tests/test_wake.py:4`). They do not establish wake accuracy, real microphone behavior, accented speech quality, echo cancellation or latency.
- Remote/model tests use fake clients and models (`tests/test_llm.py:97`, `tests/test_llm.py:131`, `tests/test_llm.py:327`). Google tests use a fake API (`tests/test_integrations.py:7`); teaching tests use fake recorder/vision/GUI implementations (`tests/test_teach.py:61`, `tests/test_teach.py:72`, `tests/test_teach.py:123`). These are valuable unit seams; live end-to-end assertions remain outstanding.
- The targeted main tests replace microphone/speaker behavior and mock proxy process launch (`tests/test_main.py:7`, `tests/test_main.py:35`, `tests/test_main.py:46`). Importing `main` does not invoke its guarded entry point (`main.py:178`). Calling `main()` or `run()` is materially different and starts real device/network/account behavior.
- The full suite is **not entirely side-effect-free**. `tests/test_computer.py:68` writes and executes a temporary Python script printing 42. The screenshot test at `tests/test_computer.py:134` mocks capture but can still create `~/Pictures/Edith` through `skills/system.py:63`. Other tests assume Windows-specific mocks. Run future tests in an isolated test profile with network/GUI/process boundaries and explicitly identify allowed temporary file and subprocess effects; `tests/conftest.py` currently provides no general side-effect guard.
- Dependencies needed for the reviewed main/agent/LLM/fastpath/STT/wake tests include pytest, numpy, anthropic, openai and psutil. `tests/test_llm.py:88` imports `httpx2`, which is not directly listed in `requirements.txt` and may be supplied transitively. The prompt-cache test (`tests/test_llm.py:353`) skips real GGUF construction but still imports `llama_cpp` through `LocalModel.warm`/`_load` (`brain/llm.py:359`, `brain/llm.py:383`). Do not infer that no native package is needed merely because the model is fake.

Future execution-based verification should identify its exact commit, interpreter/dependency environment, selected tests, real side effects allowed, results and any skips. Add focused regressions for negated confirmation, failed focus, muted capture/buffer growth, interrupted/stale turns, recipe paths/fields, account separation, effect-history loss and context overflow before enabling broader authority. Use separately scoped acceptance sessions for real audio, screen control, accounts, models, home devices and external actions. Documentation or UI completeness must never stand in for those results.
